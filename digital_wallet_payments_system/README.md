# Digital Wallet & Payments System

A FastAPI educational backend for digital wallets, simulated payments, KYC, P2P transfers, merchant payments, statements, and a double-entry ledger.


## 1. Technology

- Python 3.10+
- FastAPI and Uvicorn
- MySQL 8+ (InnoDB) / SQLAlchemy 2
- Alembic migrations
- JWT authentication and role checks
- ReportLab (PDF), CSV, qrcode
- APScheduler for periodic jobs
- Optional SMTP email notifications

## 3. Local setup (Windows PowerShell)

Run commands from the directory containing `alembic.ini` and `requirements.txt`.

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
Copy-Item .env.example .env
```

Create the MySQL database in MySQL Workbench:

```sql
CREATE DATABASE digital_wallet CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

Edit `.env` with your local database credentials and a long random JWT secret. Example (replace the placeholder; never commit the real `.env`):

```env
DATABASE_URL=mysql+pymysql://root:YOUR_MYSQL_PASSWORD@localhost:3306/digital_wallet
JWT_SECRET_KEY=replace-with-a-long-random-secret
JWT_ALGORITHM=HS256
ACCESS_TOKEN_MINUTES=30
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USERNAME=
SMTP_PASSWORD=
SMTP_FROM=
ADMIN_EMAIL=admin@example.com
```

If a database password contains URL-reserved characters (for example `@`, `#`, `/`, or `%`), URL-encode those characters in `DATABASE_URL`.

## 4. Alembic database migrations

The repository includes the initial migration `alembic/versions/e1916939096d_initial_wallet_schema.py` (revision `e1916939096d`). Apply it with:

```powershell
alembic upgrade head
alembic current
```

Expected current revision: `e1916939096d`.

After model changes, create and apply a new migration:

```powershell
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
```

Do not use `Base.metadata.create_all()` to create application tables. Review autogenerated migration files before applying them.

## 7. Swagger authentication and quick demo flow

1. Call `POST /auth/register` for the demo accounts in the table above.
2. Call `POST /auth/login` with the email and password; copy `access_token`.
3. Click **Authorize** in Swagger and enter `Bearer <access_token>` if the dialog asks for the bearer token value.
4. As the User, call `POST /wallet/pin` with `{"pin":"4826"}`.
5. Call `POST /wallet/add-money` with a new `Idempotency-Key` header (a UUID) and body:

```json
{"amount":"1000.00","source":"UPI","simulate_status":"Success"}
```

6. To demonstrate replay, execute the exact same request again with the **same** key and body. The second response should contain the `Idempotent-Replayed: true` response header and should return the saved response rather than adding funds again.
7. To demonstrate a transfer, register a second User and use their phone number as `receiver_phone`; set a PIN for the sender and use a fresh idempotency key.

Use a fresh unique idempotency key for each new operation. Reusing a key with a different user, endpoint, or request body is rejected. The transfer code requires an `otp` field for amounts above ₹5,000, but a complete OTP issue/verification flow is not implemented; use a smaller amount for the demo.

## 8. Ledger design (double-entry)

Each wallet has a ledger account. The system also creates system accounts such as `Bank Settlement`, `Fees`, `Cashback Pool`, `Withdrawal Clearing`, and `Hold`. A successful wallet movement creates corresponding debit and credit ledger entries in the same database transaction as the wallet balance update.

Example: a successful ₹100 P2P transfer from User A to User B:

| Ledger account | Entry | Amount |
|---|---|---:|
| User A wallet | Debit | ₹100.00 |
| User B wallet | Credit | ₹100.00 |
| **Total** | **Debit = Credit** | **₹100.00 each** |

The sender wallet balance decreases by ₹100 and the receiver balance increases by ₹100. The ledger records the movement; wallet balances are maintained as cached/current balances. The ledger should be treated as append-only; production corrections should use reversal entries rather than editing historical entries.

After authenticating as a user, call:

```text
GET /statements?month=2026-11&format=csv
GET /statements?month=2026-11&format=pdf
```

The response downloads the corresponding statement file. Use the month containing your demo transactions when capturing screenshots. Generated files are stored under `statements/` locally and are excluded from Git.

## 10. Reconciliation job

The application schedules reconciliation every 24 hours. For a submission screenshot, you can invoke the same job immediately from a second terminal (with the project virtual environment active and `.env` configured):

```powershell
python -c "from app.jobs.scheduler import reconcile; print(reconcile())"
```

The job compares each wallet's stored balance with its ledger credits minus debits. It reports the number of wallets checked and any mismatches. A clean result should show zero mismatches. This manual invocation runs the same reconciliation function; it does not wait for the next scheduled interval.

## 11. SMTP setup (optional)

For Gmail SMTP:

1. Enable 2-Step Verification on the Gmail account used for the demo.
2. Create a Google App Password.
3. Set `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_USERNAME` to the sending Gmail address, `SMTP_PASSWORD` to the App Password, and `SMTP_FROM` to the sender address in `.env`.
4. Restart Uvicorn after changing `.env`.

Do not put SMTP credentials in source code, screenshots, README, or GitHub. Email delivery is optional; without SMTP settings, notifications are skipped/logged rather than acting as a real payment notification service.

## 13. Assumptions and known limitations

- All payment rails are simulated; there is no real UPI, card, bank, or Razorpay integration.
- Add-money uses `simulate_status` to demonstrate success/failure outcomes.
- Public registration supports User and Merchant only. Admin is bootstrapped manually in the local demo database.
- The transaction PIN is stored as a hash. PIN lockout is implemented for P2P transfer attempts; other payment flows have simpler checks.
- The transfer endpoint checks for an OTP field above ₹5,000, but OTP generation/delivery/verification is not a complete workflow.
- Daily/monthly transfer limits, complete fraud hold/review workflows, delayed cashback settlement, merchant refunds, and full withdrawal settlement/reversal workflows are not complete.
- Merchant QR generation returns a local image path; this is a demo QR code, not a payment-network QR.
- The merchant payment path demonstrates a 1% fee; delayed 2% cashback is not fully implemented.
- Reconciliation checks wallet-level ledger balances and logs mismatches; it is not a complete financial audit/reconciliation platform.
- Use MySQL/InnoDB to exercise row-level locking (`SELECT ... FOR UPDATE`). SQLite does not provide equivalent row-lock behavior.
- Money values use `Decimal`/`Numeric(12,2)`; do not convert money to float.
- Use dummy personal data only. Do not use real Aadhaar/PAN/bank details in a demo database.
